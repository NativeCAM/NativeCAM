# Freeze Avid's post, then teach every dialect

NativeCAM can post for almost any hobby or prosumer router without becoming a scripting platform, provided today's Avid-only `MachineProfile` splits into three records (the physical frame, the controller dialect and an output profile) while `AvidMach4Post` stays frozen behind byte-for-byte golden files. The imports to build first are controller configuration files rather than posts: a pasted GRBL `$$` dump, Mach4's `Machine.ini`, LinuxCNC INI files and FluidNC YAML all carry the per-axis velocity and acceleration the run-time estimator needs, which no CAM post or Fusion machine file contains. For dialect settings the best source is the Vectric `.pp` file, a plain declarative template that nearly every router vendor publishes; NativeCAM should import the user's own copy and never bundle one, and it should not execute Fusion `.cps`, SheetCAM Lua or Carbide JavaScript posts at all. The dangerous dialect differences are about meaning rather than syntax: stock GRBL rejects `M6`, `G64`, `G90.1` and `G43 H` with error 20 while continuing to run the lines it has already buffered, FluidNC without a tool-change macro and grblHAL in one of its tool-change modes ignore `M6` silently, Masso reads `G4 P` in milliseconds where LinuxCNC reads seconds, and GRBL rejects arcs whose radii disagree by more than 0.005 mm, tighter than the 0.0127 mm fallback in today's Avid post. Avid itself has shipped Centroid CNC12 "EX" controllers as standard since late 2024, so even Avid support now needs a second dialect. A starter library of about 30 machine families from more than 20 vendors can be assembled from published specs, firmware defaults and MIT-licensed Kiri:Moto profiles, but acceleration is almost never published, so every value must say where it came from. The recommended sequence freezes Avid output, splits the model, adds a post-time validator, ships one capability-driven emitter for the Grbl family (the largest installed base), and only then adds importers, a catalogue and setup flow, `.pp` import, second-wave dialects and the proprietary long tail. That is roughly 7–10 weeks through `.pp` import and 11–17 weeks in all, and for every controller except the developer's own, access to real hardware rather than code sets the pace.

## Controller files hold the limits and vendor posts hold the dialect

No single file describes a whole machine, and that asymmetry should shape the importer. CAM post and machine files describe output and little else. A Vectric `.pp` holds the file extension, units, line endings, arc limits and quoted G-code templates, but **no travel, feed or acceleration limits** ([Vectric V12.5 post editing](https://docs.vectric.com/docs/V12.5/Aspire/ENU/Help/form/post-processor-editing/index.html)). Kiri:Moto's device profiles add bed size and maximum spindle speed, still without feed, rapid or acceleration fields ([Kiri:Moto defaults.js](https://github.com/GridSpace/grid-apps/blob/master/src/kiri/app/conf/defaults.js)). Fusion's `.mch` machine definition is the richest CAM-side file, a JSON document with per-axis travel limits, per-axis maximum feed and rapid speeds, spindle range, tool-changer facts, tool-change time and a linked post, yet a search of Autodesk's milling samples found no acceleration key at all ([Autodesk generic router .mch](https://github.com/Autodesk/cam-posteditor/blob/HEAD/vs-code-extension/res/Machines/Milling/autodesk%20generic%20router%20xyz.mch); [cam-posteditor Machines folder](https://github.com/Autodesk/cam-posteditor/tree/HEAD/vs-code-extension/res/Machines)). Vectric does keep acceleration in its Machine Configuration, but uses it only for time estimates and documents no export; the data appears to live in its versioned SQLite tool database ([Vectric Machine Configuration Management](https://docs.vectric.com/docs/V12.5/Cut2DPro/ENU/Help/form/tool-database-machine-management/index.html); [Carbide 3D community](https://community.carbide3d.com/t/c3d-tool-database/92817)).

The real kinematic limits live in controller configuration. GRBL's `$$` dump lists max rate ($110–$112, mm/min), acceleration ($120–$122, mm/s²), travel ($130–$132), spindle range ($30/$31) and junction deviation ($11) in one flat list ([GRBL v1.1 configuration](https://github.com/gnea/grbl/wiki/Grbl-v1.1-Configuration)). LinuxCNC INI files give per-axis maximum velocity and acceleration in units per second ([LinuxCNC INI](https://linuxcnc.org/docs/html/config/ini-config.html)), FluidNC YAML gives `acceleration_mm_per_sec2` and `max_rate_mm_per_min` per axis ([FluidNC config example](https://github.com/bdring/fluidnc-config-files/blob/main/contributed/6x_CNC_Controller/6x_XYZABC_Huany.yaml)), and Mach4's `Machine.ini` gives per-motor MaxVelocity, MaxAccel and soft limits ([Avid Mach4 Machine.ini](https://github.com/corbinstreehouse/Mach-4-Avid-CNC-Customizations/blob/HEAD/Profiles/AvidCNC/Machine.ini)). The importer therefore has to fill two halves of one record, a limits half from controller files or `.mch` and a dialect half from posts, which is exactly how PureCutCNC's post converter and FreeCAD's new machine model are organised ([PureCutCNC converter](https://github.com/PureCutCNC/purecutcnc/blob/HEAD/src/postProcessorConverter/README.md); [FreeCAD machine.py](https://github.com/FreeCAD/FreeCAD/blob/main/src/Mod/CAM/Machine/models/machine.py)).

Each controller format hides a trap for a naive parser. GRBL's setting numbers changed after v0.8c, so the reader must know the firmware version ([GRBL v0.8 wiki](https://github.com/grbl/grbl/wiki/Configuring-Grbl-v0.8/42eaf402ce502001ce8c7887cce33e58080ffb23)), and grblHAL adds settings that matter for safety, notably `$341=4`, which records the tool number and ignores `M6` ([grblHAL extended settings](https://github.com/grblHAL/core/wiki/Additional-or-extended-settings)). LinuxCNC's INI values are per second while its GUI shows per minute ([LinuxCNC INI](https://linuxcnc.org/docs/html/config/ini-config.html)). Mach4 is the subtle case, and it is the developer's own controller. In a published Avid profile the motor values appear to be stored in step counts: dividing by CountsPerUnit gives **10 units/s (600 in/min) of velocity and 15 units/s² of acceleration**, the soft-limit spans come to about 49.5 × 98.5 in as a 4×8 PRO should, axes map to motors through `ChildMotorN` entries that include the slaved gantry motor, and the file's spindle range tops out at **18,000 RPM** against NativeCAM's 24,000 RPM default ([Avid Mach4 Machine.ini](https://github.com/corbinstreehouse/Mach-4-Avid-CNC-Customizations/blob/HEAD/Profiles/AvidCNC/Machine.ini); [Machine.swift](../Sources/CAMCore/Model/Machine.swift)). That reading of the units rests on one file and must be checked against Mach4's Motors screen before an importer relies on it. Mach3's XML profile uses numbered per-motor tags such as `<Vel0>` and `<Acc0>` whose units remain unconfirmed ([Mach3 profile example](https://github.com/Cfree1989/Machine-profiles/blob/HEAD/Plasma/vendor/ez-router-cd/Mach%203%20Software/Mach3/LSU.xml)). Two controllers are out of reach for now: MASSO saves settings to a proprietary `.htg` file plus a printable text file that cannot be loaded back, and Centroid CNC12 keeps numbered machine parameters whose file layout is not publicly documented ([MASSO save and load](https://docs.masso.com.au/masso-settings/load-save-calibration-settings); [Acorn parameter settings](https://www.sherline.com/wp-content/uploads/2023/12/acorn_param_settings.pdf)).

On the dialect side, Vectric's format is the one worth importing. A `.pp` is entirely declarative: global statements, `VAR` lines that fix each value's format and whether it prints always or only on change, and `begin BLOCK` sections of quoted lines with bracketed tokens such as `[X]`, `[F]` and `[T]` ([Vectric V12.5 post editing](https://docs.vectric.com/docs/V12.5/Aspire/ENU/Help/form/post-processor-editing/index.html)). Its blocks (HEADER, TOOLCHANGE, SPINDLE_ON, RAPID_MOVE, FIRST_FEED_MOVE, FEED_MOVE, PLUNGE_MOVE, the arc and helical-arc moves, FOOTER) map almost one-to-one onto NativeCAM's motion events, so a complete parser is a few hundred lines of Swift. Distribution is why it matters. Vectric bundles posts for Carbide 3D, Onefinity and Avid; MASSO publishes its own; and Snapmaker, Synthetos and RealTime CNC, which builds the motion controllers in Onefinity's Redline system, publish theirs openly ([Carbide 3D community](https://community.carbide3d.com/t/new-post-processor-for-vectric-software/77335?page=3); [Onefinity forum](https://forum.onefinitycnc.com/t/vectric-post-processors-for-10-5-or-older-versions-download-links-included/640/1); [MASSO docs](https://docs.masso.com.au/cam-post-processors/vectric-vcarve-and-vectric-aspire); [Snapmaker posts](https://github.com/Snapmaker/snapmaker_cnc_post_process); [RealTime CNC posts](https://realtimecnc.com/postp/)). Licensing points toward importing users' own files: the Vectric-authored sample examined carries no licence statement, and posts installed with Vectric's software presumably fall under its EULA ([sample Grbl_mm.pp](https://github.com/fellesverkstedet/fabricatable-machines/blob/HEAD/humphrey-large-format-cnc/Settings_backup/backup/Grbl_mm.pp)).

The import should map a `.pp` onto NativeCAM's typed output settings (extension, units, line ending, arc style and radius limits, tool-change form, spin-up dwell, number formats), reading the arc style from whichever tokens the arc blocks use: incremental I/J, absolute I/J or R. It should write a conversion report of everything it could not map and, as PureCutCNC's `--strict` flag does, refuse outright when an unmapped item would change the emitted 3-axis G-code ([PureCutCNC converter](https://github.com/PureCutCNC/purecutcnc/blob/HEAD/src/postProcessorConverter/README.md)). A post with no arc blocks means linearised arcs; Vectric's own GRBL post has its arc blocks commented out, with a history note blaming arcs for slowing GRBL ([sample Grbl_mm.pp](https://github.com/fellesverkstedet/fabricatable-machines/blob/HEAD/humphrey-large-format-cnc/Settings_backup/backup/Grbl_mm.pp)).

The scripted formats are a different matter. Fusion posts are JavaScript programs written against Autodesk's proprietary post engine, and Autodesk states that use of any post is governed by its licence agreement and that the posts work only with Fusion, HSMWorks and Inventor CAM ([Autodesk post library](https://cam.autodesk.com/hsmposts)). Reimplementing that runtime is a large job with legal exposure, so at most NativeCAM should regex a few declarative header values (`extension`, `tolerance`, `maximumCircularSweep`, `highFeedrate`) out of a user's own file ([Autodesk fanuc.cps](https://github.com/Autodesk/cam-posteditor/blob/HEAD/public/fanuc.cps)). SheetCAM's Lua `.scpost` and Carbide Create Pro's JavaScript `.post` each need an embedded runtime and an emulated API ([SheetCAM example post](https://github.com/araisrobo/linuxcnc/blob/HEAD/configs/plasma-thc/SheetCam/SheetCamEMCPlasma.scpost); [Carbide 3D Hub FAQ](https://carbide3d.com/hub/faq/create-pro-custom-post-processor)). FreeCAD's new `.fcm` machine file is promising as open JSON with per-axis limits and maximum velocity, but it exists only in the 26.3 release candidate, not in stable 1.1, so it merits watching rather than building for yet ([FreeCAD 26.3rc2](https://github.com/FreeCAD/FreeCAD/releases/tag/26.3rc2)). Kiri:Moto's 28 CNC profiles are the opposite case: MIT-licensed seed data that can be bundled with attribution once a loader handles the two JSON key schemes they use ([grid-apps CNC profiles](https://github.com/GridSpace/grid-apps/tree/master/src/kiri/dev/cam); [grid-apps licence](https://github.com/GridSpace/grid-apps/blob/master/license.md)).

## Four controller families disagree on the words that cut

The controllers routers actually run fall into four families. The Grbl lineage (GRBL 1.1, grblHAL, FluidNC and Carbide Motion on its Grbl base) is strict: unknown words raise errors, and there is **no `G64`, no `G90.1` and no `G43 H`** ([gnea/grbl README](https://github.com/gnea/grbl); [FluidNC GCode.cpp](https://github.com/bdring/FluidNC/blob/main/FluidNC/src/GCode.cpp)). LinuxCNC and its relatives, PathPilot and Buildbotics through the CAMotics interpreter, accept a rich dialect with `G64 P`, `G90.1`, canned cycles and `G43 H` ([LinuxCNC G-codes](https://linuxcnc.org/docs/html/gcode/g-code.html); [CAMotics G-code](https://camotics.org/gcode.html)). The Fanuc-flavoured PC controls (Mach3, Mach4, UCCNC, Masso and Centroid CNC12) support canned cycles and macro-driven `M6`. The proprietary controls, ShopBot's OpenSBP, RichAuto and Weihong DSP handhelds and Onefinity's new Redline system, have so little public documentation that the vendor's own post is effectively the specification. One assumption needs correcting along the way: Onefinity does not use FluidNC. Its machines went from Buildbotics (2020–2025) to Masso G3 on the 2023 Elite, and then to Redline with RTX controllers from 2025 ([Onefinity: which controller](https://www.onefinitycnc.com/post/which-controller-does-my-onefinity-machine-use)).

### An ignored tool change keeps cutting with the old bit

**Tool changes are the most dangerous split, because several controllers can skip `M6` without stopping the job.** Stock GRBL treats `M6` like any unsupported M-code and raises error 20 ([grbl gcode.c](https://github.com/gnea/grbl/blob/master/grbl/gcode.c)). A block with an error is discarded, but under character-counting streaming the lines already in GRBL's receive buffer keep executing, so an `M6` that nobody intercepts lets the next tool's toolpath run with the old bit ([grbl interface.md](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md)). FluidNC hands `M6` to a configured changer or macro and, with neither configured, merely records the tool number ([FluidNC GCode.cpp](https://github.com/bdring/FluidNC/blob/main/FluidNC/src/GCode.cpp)); grblHAL does the same deliberately when `$341=4` ([grblHAL tool change wiki](https://github.com/grblHAL/core/wiki/Manual,-semi-automatic-and-automatic-tool-change)). Sienci's gSender offers Ignore, Pause or a wizard for tool changes, and one of its issues argues that Ignore should warn because behaviour after an ignored `M6` is undefined ([gSender tool changing](https://resources.sienci.com/view/gs-tool-changing/); [gSender issue #515](https://github.com/Sienci-Labs/gsender/issues/515)). UCCNC's M6 macro does nothing until it is enabled in settings ([CNC Drive forum](https://forum.cncdrive.com/viewtopic.php?p=33541)). Little wonder that Carbide Create reportedly writes tool changes as `M0 ;T302` with no `M6` at all ([Onefinity forum](https://forum.onefinitycnc.com/t/gcode-where-is-m6-tool-change/14739)).

The tool-change strategy is therefore a property of the whole chain (firmware, its settings and the program that streams the file), not of the controller's name. NativeCAM needs five strategies. Plain `T# M6` suits Mach4 with Avid's macro, LinuxCNC, Masso, CNC12, and gSender or CNCjs set to pause. `T# M6` followed by `G43 H#` suits ATC machines and controls whose `M6` leaves the length offset alone, which LinuxCNC documents explicitly ([LinuxCNC M-codes](https://linuxcnc.org/docs/html/gcode/m-code.html)). A sequence of `M5`, retract, `M0` and a comment suits raw GRBL, FluidNC without a macro and UCCNC with M6 disabled. One file per tool suits DSP handhelds and serves as the fallback that works anywhere, and single-tool jobs need no change sequence at all. Tool-length offsets split along the same line: GRBL and FluidNC accept only the dynamic `G43.1 Z`, so a post must never send them `G43 H`, and Carbide Motion accepts `G43` and `G49` but ignores them ([gnea/grbl README](https://github.com/gnea/grbl); [Carbide 3D supported G-codes](https://carbide3d.com/hub/faq/supported-gcodes)).

### The same `G4 P` means seconds on one controller and milliseconds on another

**Dwell units are the most dangerous silent difference.** LinuxCNC reads `G4 P` in seconds, Masso reads milliseconds and documents `G04 P2000` as two seconds, and Mach3 makes the unit a configuration choice that has caught out SheetCAM users ([LinuxCNC G-codes](https://linuxcnc.org/docs/html/gcode/g-code.html); [Masso G04](https://docs.masso.com.au/supported-g-codes/g04-dwell?ln=en); [Langmuir forum](https://forum.langmuirsystems.com/t/mach3-pierce-delay-issue/3542/9)). Mach4's sources conflict. The official Mill manual says seconds, while MachMotion's reference says milliseconds when P has no decimal point and seconds when it has one, the same Fanuc-style rule Haas uses ([Mach4 Mill G-code manual](https://www.machsupport.com/wp-content/uploads/2014/05/Mach4%20Mill%20GCode%20Manual.pdf); [MachMotion Mach4 reference](https://support.machmotion.com/books/software/page/mach4-g-code-and-m-code-reference); [Haas G04](https://www.haascnc.com/service/codes-settings.type=gcode.machine=mill.value=G04.html)). Writing P with a decimal point is correct under both readings, and today's post already does so with `G04 P4.00` ([AvidMach4Post.swift](../Sources/CAMCore/Post/AvidMach4Post.swift)). A Masso emitter must write a whole number of milliseconds instead. For GRBL no fetched source states the unit, so it must be confirmed in GRBL's own source before the Grbl emitter writes any dwell. The same rule binds the parser: `GCodeParser` reads every `G4 P` as seconds, so a Masso file loaded into the simulator would estimate a two-second dwell as **2,000 seconds** ([GCodeParser.swift](../Sources/CAMCore/Post/GCodeParser.swift)).

### GRBL's arc check is tighter than today's fallback, and a rejected arc keeps cutting

Arcs travel well between controllers if a post emits incremental I/J and never `G90.1` (which GRBL and FluidNC reject), avoids R-format arcs (GRBL cannot do R-format full circles), and keeps the start and end radii consistent ([grbl gcode.c](https://github.com/gnea/grbl/blob/master/grbl/gcode.c); [FluidNC GCode.cpp](https://github.com/bdring/FluidNC/blob/main/FluidNC/src/GCode.cpp)). GRBL, FluidNC and LinuxCNC share one radius check: an arc fails when its radii differ by more than 0.5 mm, or by more than both 0.005 mm and 0.1% of the radius ([grbl gcode.c](https://github.com/gnea/grbl/blob/master/grbl/gcode.c); [LinuxCNC G-codes](https://linuxcnc.org/docs/html/gcode/g-code.html)). Today's post falls back to a straight line only when the rounded radii differ by more than 0.0005 in, or 0.0127 mm ([AvidMach4Post.swift](../Sources/CAMCore/Post/AvidMach4Post.swift)). That suits Mach4 but is too loose for GRBL on **any arc under 12.7 mm radius**: a 3 mm arc whose radii differ by 0.01 mm passes NativeCAM's check and draws error 33. The Grbl emitter therefore needs a fallback threshold below 0.005 mm, at least three decimals in mm and four in inches, and I/J computed from the rounded start point as the Avid post already does. Splitting arcs at 180° is safe everywhere, and where a controller's arc handling is undocumented, as on RichAuto and Redline, arcs should go out as lines until tested. Because GRBL discards an erroring block and carries on, a rejected arc is not a stop: the tool cuts straight from the arc's start to the next target. **On this family, checking the file before export is a safety requirement, not a convenience.**

### The remaining differences are mechanical but must be encoded

The rest of the split is mechanical, though each item still has to live in the controller profile. GRBL rejects `G64` with error 20 and accepts `G61` but ignores it, LinuxCNC takes `G64 P<tolerance>`, and Mach4's `G64` takes no P ([grbl gcode.c](https://github.com/gnea/grbl/blob/master/grbl/gcode.c); [LinuxCNC G-codes](https://linuxcnc.org/docs/html/gcode/g-code.html); [Machsupport forum](https://www.machsupport.com/forum/index.php?topic=35121.0)). Every word in Avid's safety line, `G40`, `G49` and `G80` included, is legal GRBL, and the `G91.1` after it is a no-op there, so a Shapeoko fed today's output would first hit error 20 at the bare `G64` that follows ([gnea/grbl README](https://github.com/gnea/grbl)). Canned cycles exist on grblHAL, LinuxCNC, Mach4 and Masso but not on GRBL or FluidNC, so drilling should be written out as G0/G1 moves by default ([grblHAL core](https://github.com/grblHAL/core); [Masso docs](https://docs.masso.com.au/supported-g-codes/g04-dwell?ln=en)). GRBL's line buffer holds **80 characters** by default and FluidNC's **127**, against 256 on LinuxCNC, and GRBL caps line numbers at 9,999,999 and tool numbers at 255 (error 38), a limit that now matters because imported tool libraries keep their source numbering ([grbl config.h](https://github.com/gnea/grbl/blob/master/grbl/config.h); [FluidNC GCode.cpp](https://github.com/bdring/FluidNC/blob/main/FluidNC/src/GCode.cpp); [LinuxCNC overview](https://linuxcnc.org/docs/html/gcode/overview.html); [grbl interface.md](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md)). Stock GRBL compiles `M7` out, which is why GRBL router posts put the dust collector on `M8` while Avid's profile uses `M7` ([grbl config.h](https://github.com/gnea/grbl/blob/master/grbl/config.h); [Machine.swift](../Sources/CAMCore/Model/Machine.swift)). Carbide Motion ignores `G54`–`G59` in files ([Carbide 3D supported G-codes](https://carbide3d.com/hub/faq/supported-gcodes)), and Axiom's RichAuto controller reportedly runs in metric only ([Vectric forum](https://forum.vectric.com/viewtopic.php?p=190173)). Units belong to the controller in every case; when a user's mm post met an inch-mode EX controller, Avid staff replied that "your post and your machine should all be in the same units" ([Avid forum](https://forum.avidcnc.com/t/z-axis-work-envelope-exceeded-what-am-i-missing/4398)).

The Centroid column's tool block (`M5`, a comment, `T[T]M6`, then a `G43` line) and `.cnc` extension come from an Avid owner's customisation of Vectric's EX post, which remains the best reference until Centroid's own manual can be read ([Corbin's Treehouse](https://www.corbinstreehouse.com/blog/2023/05/avid-cnc-atc-post-processor-setup-vectric-vcarve-vectric-aspire)).

### Compiled emitters driven by capability profiles, not user scripts

The way to handle all this is a small set of compiled, tested emitters driven by typed capability profiles, not a template engine users program, which matches FreeCAD's stated direction of moving configuration out of the post and into the machine record ([FreeCAD dev wiki: Machines](https://github-wiki-see.page/m/sliptonic/FreeCAD/wiki/Machines)). A single `GenericGCodePost` would take a `DialectCapabilities` value describing what the controller accepts (maximum line length; allowed G, M and parameter words; what `M6` means and which tool-length style applies; blending syntax; canned-cycle support; dwell unit and decimal policy; I/J mode; comment syntax; accepted unit modes; highest tool number) together with an `OutputOptions` value holding the choices users actually make. Vendor posts for the same controller differ along six axes: whether arcs are emitted, the tool-change form, the tool-length-offset line, the dwell after spindle start, units and extension, and retract style (`G28` versus `G53 Z`) ([Corbin's Treehouse](https://www.corbinstreehouse.com/blog/2023/05/avid-cnc-atc-post-processor-setup-vectric-vcarve-vectric-aspire); [Fusion post library](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-POST-PROCESSOR-LIBRARY-REF.htm)). Those six should be the user-facing options, defaulting to whatever the vendor's own post does. Header, footer and tool-change snippets can exist, but each must be checked against the target before posting, flagging unknown codes, `G28` or `G30` unless the profile allows them, unit changes and `G92`; Kiri:Moto's own warning that not every macro works in every context shows why free text needs a checker ([Kiri:Moto docs](https://docs.grid.space/kiri-moto/CAM/machines)). `AvidMach4Post` stays its own emitter, untouched, and merges into the generic emitter only once the generic emitter, configured for Mach4, reproduces every Avid golden file byte for byte. For the proprietary long tail, the user's imported vendor `.pp` becomes the specification: NativeCAM either maps it onto the generic emitter or, for dialects the emitter cannot express such as ShopBot's OpenSBP, renders it as a template, always behind the validator and always labelled unverified.

## Thirty-odd machine families from 20-plus vendors make a credible starter library

Published data is reliable for work area, spindle, controller family and tool-change type, patchy for maximum feed and rapid, and almost absent for acceleration. Even the patchy numbers conflict. For the Shapeoko 5 Pro, one user reports 5,080 mm/min X/Y as configured while another found it capped at 7,000 mm/min, and Carbide's spec page leaves travel blank ([Shapeoko 5 Pro specs](https://carbide3d.com/shapeoko/shapeoko5pro-specs/); [Carbide 3D community](https://community.carbide3d.com/t/maximum-speed-shapeoko-5-pro/91269)). Community `$$` dumps for the Genmitsu 3018 give X acceleration as 30, 50 or 3,000 mm/s² ([softsolder](https://softsolder.com/2019/08/22/cnc-3018-pro-grbl-configuration/)). Usable acceleration comes only from firmware defaults and from vendors who chose to publish it. GRBL's upstream profiles give the Shapeoko 3 **400 mm/s²** and the X-Carve and BobsCNC **500 mm/s²** ([grbl defaults.h](https://github.com/gnea/grbl/blob/master/grbl/defaults.h)); Sienci's per-model gSender defaults give the LongMill **750 mm/s²** and the AltMill **1,500 mm/s²** ([gSender machine defaults](https://github.com/Sienci-Labs/gsender/tree/master/src/app/src/features/Config/assets/MachineDefaults)); and Onefinity publishes official values for Vectric's estimator, 29.528 in/s² (750 mm/s²) for Buildbotics machines and 19.685 in/s² (500 mm/s²) for Masso Elites ([Onefinity acceleration FAQ](https://forum.onefinitycnc.com/t/machine-configuration-management-acceleration-vectric-12-5-values-faq/33544)). Avid publishes nothing; owners report that Mach4 ships at about **50 in/s² (1,270 mm/s²)** ([Avid forum](https://forum.avidcnc.com/t/mach4-motor-accel-a-macro-and-post-combo/2505)).

No current controller market-share survey exists. CNCCookbook's 2012 survey put Mach3 at 66% of hobby controls, but it predates GRBL's rise, and its 2017 edition already showed GRBL and Mach4 taking share ([CNCCookbook 2012](https://www.cnccookbook.com/cnc-control-market-shares-what-are-the-most-popular-controls); [CNCCookbook 2017](https://www.cnccookbook.com/choose-best-cnc-control-2017-cnc-control-survey-results)). Every current signal points to the Grbl family as the largest base by unit count: Autodesk describes its Grbl post as one of the most used on the milling side, and gSender ships machine profiles for more than a dozen GRBL machine makers ([Autodesk Grbl blog](https://www.autodesk.com/products/fusion-360/blog/fusion-360-grbl-post/); [gSender defaultMachineProfiles.ts](https://github.com/Sienci-Labs/gsender/blob/master/src/app/src/features/Config/assets/MachineDefaults/defaultMachineProfiles.ts)). The other trend is frames keeping their names while their controllers change underneath. Avid chose Centroid technology for its next-generation EX controllers, now standard on new kits and offered as an upgrade, and its PRO4896 page lists CNC12 control software ([MfgNewsWeb](https://www.mfgnewsweb.com/archives/4/67461/Controls-dec24/ad_info.aspx); [Avid PRO4896](https://www.avidcnc.com/pro4896-4-x-8-cnc-router-machine-p-1337.html)). Onefinity has changed controllers twice, CAMaster moved from WinCNC to Centroid, and Sienci's LongMill MK2 shipped with either a GRBL LongBoard or a grblHAL SuperLongBoard ([Onefinity](https://www.onefinitycnc.com/post/which-controller-does-my-onefinity-machine-use); [Sawmill Creek](https://sawmillcreek.org/goto/post?id=3287071); [Sienci LongMill MK2 handbook](https://resources.sienci.com/view/lmk2-handbook/)). A library entry must therefore be a frame carrying a list of known controllers, not a fixed machine-and-post pair. Avid's line also differs from NativeCAM's presets: the 2×4 model is the PRO4824 and no "PRO2448" exists, the benchtops are the Benchtop PRO and Benchtop Standard in 2424 and 2436 sizes, and the drive tiers of 250/400/600 IPM cut and 500/800/1,200 IPM rapid are confirmed ([cncrouterinfo PRO4824](https://cncrouterinfo.pages.dev/routers/avid-pro4824); [Avid Benchtop PRO 2436](https://www.avidcnc.com/benchtop-pro-2436-2-x-3-cnc-machine-p-1333.html); [Avid PRO6060](https://www.avidcnc.com/pro6060-5-x-5-cnc-router-kit-p-634.html)).

Every piece of seed data needs a licence trail. Kiri:Moto's profiles are MIT-licensed and can be bundled with attribution, which fits the README's rule that fixtures come only from permissively licensed projects recorded in a `SOURCE.md` ([grid-apps licence](https://github.com/GridSpace/grid-apps/blob/master/license.md); [README](../README.md)). GRBL's `defaults.h` is GPL code and gSender's licence was not checked, so their numbers can be recorded as cited facts but the files should not be copied. Autodesk's MIT-licensed `cam-posteditor` repository holds 45 sample `.mch` files that make good importer fixtures ([cam-posteditor](https://github.com/Autodesk/cam-posteditor)), and PureCutCNC's Apache-2.0 design can be studied freely, though the vendor posts among its test fixtures carry their original owners' terms and need checking one by one ([PureCutCNC](https://github.com/PureCutCNC/purecutcnc)). In the app, vendor-checked and community entries should look visibly different, each carrying its source URL and the firmware it was last tested on, and the catalogue can accept pull requests the way Kiri:Moto's does ([Kiri:Moto docs](https://docs.grid.space/kiri-moto/CAM/machines)). At launch only one entry can honestly be marked verified: the developer's PRO6060 on Mach4.

## Frame, controller and output profile must become separate records

The mature CAM products keep machine, post and cutting data apart. Vectric links each machine to several posts, each pinned to a version or set to follow the latest, with one as the default, and its save dialog lists only the posts linked to the chosen machine ([Vectric Machine Configuration Management](https://docs.vectric.com/docs/V12.5/Cut2DPro/ENU/Help/form/tool-database-machine-management/index.html); [Vectric Save Toolpaths](https://docs.vectric.com/docs/V12.5/Aspire/ENU/Help/form/Save%20Toolpaths/index.html)). Fusion links a post to a machine definition and handles variants through post properties ([Fusion: link a post processor](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-MACHINE-LINK-POST.htm)). FreeCAD's new model goes furthest, folding output settings into the machine record so that writing a new post becomes rare ([FreeCAD dev wiki: Machines](https://github-wiki-see.page/m/sliptonic/FreeCAD/wiki/Machines)). Vectric's other habit, a separate post file for each variant such as "Shapeoko (mm)" and "Shapeoko (in)", multiplies the choices and invites the wrong-post errors that fill every vendor's forum. NativeCAM should take Vectric's machine-to-several-outputs link and version pinning, and FreeCAD's typed options.

| Record | What it holds | Today's `MachineProfile` fields that move there |
|---|---|---|
| Frame | Vendor, model and size; per-axis travel, maximum feed, rapid and acceleration; spindle kind, RPM range and power; tool-change hardware (manual, or ATC with slots); probing hardware (touch plate, tool setter, BitSetter); Avid drive-tier preset; where each value came from | `model`, `travel`, `drive`, `spindle`, `minRPM`, `maxRPM`, `rapidRateForEstimates`, `rapidRateZ`, `maxFeedRate`, `accelerationXY`, `accelerationZ`, `roughingSmoothing` |
| Controller | Family and firmware version; sending program (Grbl family); unit mode; capability set; what `M6` and its macro actually do; planner model for estimates (Mach4 constant velocity with exact-stop G0, Grbl junction deviation, LinuxCNC `G64 P`) | `outputUnits` (as the controller's unit mode), `junctionDeviation`, `lookaheadLines`, `toolChangeSeconds` |
| Output profile | Emitter ID and version; extension, line ending and decimals; arcs and arc tolerance; tool-change strategy and length offset; blending; drilling; retract and park style; accessory outputs; spin-up dwell; line numbers; checked snippets | `toolChange`, `dustCollection`, `spindleSpinUpDwell`, `outputArcs`, `arcFitTolerance`, `lineNumbers` |
| Machine setup (library item) | One frame, one controller, and one or more output profiles with a default; stable ID; schema version; revision | — |

### Old project files keep opening, and older builds refuse what they cannot post

Backward compatibility decides how this gets built. Every `.nativecam` file embeds a `MachineProfile` decoded with Swift's synthesized `Codable`; its `model` is a required `AvidModel`, and its motion fields were already added as optionals so older files still load ([Project.swift](../Sources/CAMCore/Model/Project.swift); [Machine.swift](../Sources/CAMCore/Model/Machine.swift)). The safe path continues that pattern. Keep every existing key and its meaning, add optional `controller`, `outputs`, `libraryID` and `libraryRevision` fields plus a provenance entry per value, treat a missing controller as "legacy Avid Mach4" routed to the untouched `AvidMach4Post`, and give non-Avid frames `model: .custom` plus a catalogue ID. One hazard needs a deliberate fix. Swift's synthesized decoder ignores keys it does not know, so an older NativeCAM build opening a project saved for a GRBL machine would drop the `controller` field and quietly post Mach4 code, `G64` and all. Writing `formatVersion` 2 whenever a project uses anything but the legacy controller closes the gap, because `Project.decode` already refuses files from a newer format, while projects still on the legacy Avid controller keep version 1 and open everywhere ([Project.swift](../Sources/CAMCore/Model/Project.swift)).

New enums should decode unknown raw values to an `unknown` case so that future additions degrade gracefully. Each project should keep a full resolved snapshot of its machine, not merely a library reference, together with the emitter version, so that it re-posts identically years later. When a library entry changes, the app should offer the update with a diff of the resulting G-code and never apply it silently: Fusion warns that customised posts saved beside installed ones can be overwritten when it updates, and its February 2025 update broke one router user's manual tool changes ([Fusion post processing overview](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-POST-PROCESSING-OVERVIEW.htm); [Autodesk forum](https://forums.autodesk.com/t5/fusion-manufacture-forum/errors-since-feb-2025-update/m-p/13387763)). The library belongs beside `tools.json`, as `machines.json` in Application Support, replacing the default machine that `AppDefaults` keeps in UserDefaults today. IDs should stay stable across imports, so that re-importing updates an entry instead of duplicating it, unlike LightBurn, which creates a duplicate device on conflict ([ToolLibrary.swift](../Sources/NativeCAM/ToolLibrary.swift); [LightBurn devices](https://docs.lightburnsoftware.com/2.1/Reference/Devices/)).

### The machine importer should copy the tool importer

The importer should follow the tool-import pattern closely. A `MachineLibraryImporter` in CAMCore would load a file or pasted text and recognise the format from its content: a list of `$`-numbered settings is GRBL, an INI with `[Motor0]` sections is Mach4 and one with `[TRAJ]` is LinuxCNC, YAML with an `axes:` map is FluidNC, JSON with `kinematics` is Fusion, and a file with `begin HEADER` is a Vectric post. It would return a `MachineImport` holding the format, partial records, skipped items and notes, just as `ToolImport` carries tools and skipped tools ([ToolLibraryImporter.swift](../Sources/CAMCore/Import/ToolLibraryImporter.swift)). Because most sources fill only half a record, the picker sheet must let the user apply an import to an existing machine as well as create a new one: a `$$` paste fills a frame's limits and a controller's settings, while a `.pp` fills an output profile. Every converted or estimated value gets a note on the item, such as "acceleration 15 in/s², from Machine.ini MaxAccel ÷ CountsPerUnit" or "Z acceleration estimated from the belt-drive default", so the user can see which numbers are theirs.

### Setup should ask exactly what users get wrong

The setup flow should ask, in order, about the things forum threads show users getting wrong. It opens with vendor, model and size from the catalogue, a generic machine, or an import from file. It then asks for the controller whenever the frame has more than one known option, because a wrong choice is a documented failure: an Avid EX owner whose work Z read zero at the top of travel turned out to be using the wrong post for the CNC12 controller ([Avid forum: EX CNC12 Z trouble](https://forum.avidcnc.com/t/ex-cnc12-z-axis-trouble/4351)). For the Grbl family it asks which program streams the file and how that program treats `M6`, and refuses `T# M6` until the user confirms the sender pauses on it. It asks the controller's unit mode and explains that the controller will not convert units. It asks how tools change (by hand with a touch plate, by hand with a tool setter, by ATC, or single tool only) and how the spindle and dust collector are switched. It offers to read a `$$` paste or a `Machine.ini` to improve run-time estimates and otherwise fills class defaults marked as estimated. It closes with a plain-language summary ("Output in inches, G20. Tool changes stop the spindle and pause with M0; re-zero Z with your touch plate, then press Cycle Start. Dust collector on M8."), a preview of a short sample program and an air-cut test file. Two anti-patterns stay out of scope. NativeCAM should never write controller settings, as Easel reportedly does when an X-Carve is selected during setup ([Easel support](https://support.easel.com/hc/en-us/articles/360012642474)), and it should never give a manual-change machine a multi-tool file without a defined pause-and-re-zero sequence, which Vectric enforces by requiring a separate toolpath file per cutter for manual changes ([Vectric Save Toolpaths](https://docs.vectric.com/docs/V12.5/Aspire/ENU/Help/form/Save%20Toolpaths/index.html)).

## Ship the Grbl family first, behind golden files and a validator

The order follows from three facts. Avid output must not change, yet nothing pins it today: the current post tests check that particular lines are present rather than comparing whole files, and the repository holds no G-code golden fixtures, so freezing comes first ([PostTests.swift](../Tests/CAMCoreTests/PostTests.swift)). The Grbl family is the best next target because it has the largest installed base, its behaviour is documented down to the parser source, and one emitter covers four firmwares; Fusion's library has no grblHAL, FluidNC or Sienci post at all, so those users already fall back to a generic Grbl post ([Fusion post library](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-POST-PROCESSOR-LIBRARY-REF.htm)). And a validator protects the developer's own machine as much as anyone's, so it lands before any new dialect.

### Verification must check the file the machine will actually run

The verification pipeline borrows from three places: FreeCAD's golden-output post tests, which compare exact G-code for precision, inch conversion, line numbers and the `M5` / `M6 T2` / `G43 H2` tool-change sequence ([TestMach3Mach4Post.py](https://raw.githubusercontent.com/FreeCAD/FreeCAD/main/src/Mod/CAM/CAMTests/TestMach3Mach4Post.py)); the commercial verification industry, which insists on simulating the posted code the machine will run ([VERICUT](https://vericut.com/products/vericut-verification)); and GRBL's own error list, a ready-made rule set ([grbl interface.md](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md)). Every emitter gets whole-file golden outputs, so any change to an emitter or a catalogue entry appears as a reviewable diff, the same diff the app shows a user before updating a machine. Every exported file is then parsed back under the target's modal rules and compared with the internal toolpath within a tolerance, the only check that catches bugs like the Fusion case where a simulation looked right over G-code whose X values were doubled ([Autodesk forum](https://forums.autodesk.com/t5/fusion-manufacture/internal-profile-simulation-does-not-match-gcode/m-p/12804423)).

Lint rules apply per target. They require an explicit `G20` or `G21` in the first lines matching the controller's unit mode, enforce the line-length limit, and allow only the G, M and parameter words the target accepts, with no I, J, K or R off arc lines and no H off a `G43` line (GRBL error 36). They also demand an F word before the first feed move (error 22), radius consistency at the target's arc tolerance (error 33), tool numbers within range (error 38), a complete change sequence for every new tool on a manual-change machine, feeds and spindle speeds within the frame's limits, and a safe retract before the first move after a change. The envelope check compares the job's extents, retract heights and park moves with machine travel, and Z depth plus tool stick-out with Z travel; it cannot lean on controller soft limits, which GRBL enforces only when homing is enabled ([Grbl v1.1 configuration](https://github.com/gnea/grbl/wiki/Grbl-v1.1-Configuration/f7a8ef43bd2bc0dab6e7cbdd31a05668d22d3394)). An air-cut variant raises Z by a chosen amount, following Autodesk's advice to set offsets to a safe position and dry-run the machine ([Autodesk post training guide](https://cam.autodesk.com/posts/posts/guides/Post%20Processor%20Training%20Guide.pdf)). Hard errors block export (an `M6` to a GRBL setup that does not handle it, `G64` to the Grbl family, a dwell in the wrong unit, post units that differ from the controller's), while warnings such as a job larger than travel, a spindle speed above maximum or arcs on an arc-sensitive controller require acknowledgement.

| What exactly does Avid's Mach4 M6 macro (`m6.mcs` in the profile's Macros folder) do: retract to machine Z, move to a change position, stop the spindle, prompt, run the touch plate? | It decides whether manual M6 needs `G43 H#`, whether NativeCAM's own retract and `M05` before `T#M6` duplicate the macro, and which modes the macro leaves behind | Read the macro; run a two-tool air program and watch Mach4's offset readouts |
| Does the touch-plate routine set work Z or a tool-length offset? | An active stale `G43 H` has caused a known Avid touch-plate bug ([Avid forum](https://forum.avidcnc.com/t/avid-touch-plate-bug-when-a-tool-height-is-set-and-active/1789?page=2)) | Same test, with an offset deliberately active |
| What are your real motor counts, velocities, accelerations, soft limits and spindle range? | Estimator inputs; the published Avid file shows 18,000 RPM against NativeCAM's 24,000 default | Export `Machine.ini`; compare with Configure > Control > Motors |
| Is `M7` the dust-collector relay on your profile, and is anything wired to `M8`? | Generic accessory mapping must keep Avid's `M07` | Toggle each from the MDI line |
| Does your Mach4 build read `G04 P2` as 2 s or 2 ms? | Output already uses decimals, but the parser and imported files need the rule | Time both forms from the MDI line |
| Will NativeCAM target Avid EX (CNC12), and who will test it? | It has been Avid's standard controller since late 2024 | Recruit EX owners; obtain Avid's EX Vectric post |
| Which other controllers can you reach through owners or bench boards? | No dialect should be marked verified without hardware | A beta programme; a GRBL board on the bench |
| Should NativeCAM ever connect to a controller, to send files or read `$$` live? | Writing controller settings is the Easel anti-pattern; reading is the most that is defensible | Product decision |
| Should the Grbl emitter output arcs by default, or lines as Vectric's GRBL post does? | Arcs cut block counts; Vectric found they slowed GRBL | Time both on a GRBL machine |
| Should the README's Avid-first positioning change, and who reviews community catalogue entries? | It affects defaults, badges and support load | Product decision |

### What has to run on real machines

The developer's PRO6060 on Mach4 carries the first round of hardware checks, and most of them are cheap.

| Test on the PRO6060 | Pass when |
|---|---|
| Golden replay of the frozen jobs after stages 1 and 2 | Files are byte-identical (no machine needed), and one air cut confirms nothing else changed |
| M6 macro trace | The sequence is written down and the `G43 H` question is settled |
| Dwell timing for `G04 P2` and `G04 P2.0` | The rule is known |
| `Machine.ini` import cross-check | Imported values match Mach4's Motors screen |
| Job placed near the travel limits | NativeCAM warns before Mach4's soft limits trip |
| Air-cut variant | It runs at the chosen Z offset with unchanged X and Y |
| Estimator timing suite of lines, squares, circles at several radii, short-segment zig-zags, rapids and a helix | Estimates agree with stopwatch times |

Every other dialect needs one acceptance program per output profile, covering the unit declaration and safety line, a square, circles from 1 mm to 50 mm radius in all four quadrants, a helix, an arc over 180° to confirm splitting, a three-second dwell, two tool changes, the dust output switched on and off, park and program end, and, for the Grbl family, lines near the length limit. It should run three times. The first run uses the controller's check mode where one exists, since GRBL's `$C` mode processes a program without moving the machine ([grbl interface.md](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md)). The second is an air cut on an owner's machine, and the third a shallow cut in scrap, where measured circle diameters expose unit and arc errors and depths after each tool change expose length-offset and re-zero errors. CAMotics, a GPL G-code simulator that runs on macOS, gives an independent second look at the output ([LinuxLinks: CAMotics](https://www.linuxlinks.com/camotics-3-axis-cnc-gcode-simulator/)), but it cannot replace hardware, because only a controller's own interpreter decides what that controller accepts.

## Conclusion

The research changes what "supporting any machine" means. G-code syntax is the easy part and fits in a capability table. The hard part is how a firmware-and-sender chain behaves: whether `M6` actually stops the machine, whether a rejected line halts the job or is skipped while cutting continues, whether `P2` means two seconds or two milliseconds. No single file answers those questions, so the setup flow has to ask and the validator has to enforce. That produces an asymmetry worth designing around. The Grbl family looks hostile because it is strict, but its strictness plus `$C` check mode makes it the safest family to support without owning one, while the truly dangerous controllers are the forgiving ones that ignore an `M6` or read a dwell in another unit without complaint.

Two implications reach beyond the plan itself. "Avid support" is already a multi-dialect problem, because new Avid machines ship on CNC12, so the abstraction NativeCAM needs for strangers' machines is the one Avid's next customers need too, and building it carefully protects the developer's own use case rather than diluting it. And controller configuration files are the only files that carry acceleration, which Fusion's documented machining-time model leaves out and Kiri's profiles never store ([Fusion machining time](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-MACHINING-TIME-OVERVIEW.htm)). Importing them turns NativeCAM's acceleration-aware estimator from an Avid feature into an advantage on every machine it can read. Until a dialect has run on real hardware, though, its honest label is "unverified", and the README's air-cut-first rule applies with extra force to controllers nobody on the project owns.
